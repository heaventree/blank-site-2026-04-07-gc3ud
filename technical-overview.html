Identity & access management

JAM Safety runs thousands of staff across concurrent events in multiple countries. The IAM system is designed from the ground up for this scale — fine-grained permissions, group-based staff pools, event-scoped access, and a full admin override layer. No user ever sees data they shouldn't, and no permission change goes unlogged.

The six base roles

Every user is assigned exactly one base role. Permissions are additive within a role — admins can grant additional capabilities at the user level without changing the role itself.

table_chartFeature permission matrix✓ full   ◎ read-only   ✗ no access   ★ admin-configurable
Granular permission architecture
tunePer-user overrides

Beyond the base role, any user can receive individual capability grants or denials without changing their role. This handles edge cases at scale without role explosion.

-- Permission resolution order (highest wins) 1. UserPermissionDeny -- explicit block (security) 2. UserPermissionGrant -- individual override 3. GroupPermission -- staff pool / crew rules 4. EventPermission -- event-scoped access 5. RolePermission -- base role defaults
groupStaff pools & group permissions

For large events with hundreds of field staff, manage permissions at pool level. A "Steward Crew" pool might have different access than a "Supervisor Crew" — and these are set once, applied to all members instantly.

Pool: Festival Stewards (847 users)
Assigned: submit_site_report, submit_incident, view_safety_docs
Denied: view_staff_contacts, view_manpower_data
Pool: Senior Supervisors (23 users)
Assigned: submit_*, view_*, approve_toolbox_talks
Override: view_incident_full_detail = true
eventEvent-scoped access

A field staff member assigned to Event A cannot see Event B's data — not the documents, not the reports, not the incident list. Access is automatically revoked when the event ends. No manual cleanup required.

-- How event scope is enforced SELECT * FROM incidents WHERE event_id = current_user_event_scope() AND check_permission(user_id, 'view_incident') -- Row-level security enforced at DB layer

Ops Admins can grant time-limited permissions — useful for contractor assessors who need read-only access to a document library for 48 hours, or for temporary supervisory cover during sick leave.

AI model strategy

No single model is the cheapest, fastest and most capable for every task — so JAM Safety OS is not locked to one vendor. The platform routes every AI call through OpenRouter, a unified gateway that gives access to Claude, GPT, DeepSeek, Qwen and dozens of other models behind one API. Tasks are matched to models on a 4-tier complexity ladder: day-to-day lookups and routing decisions run on near-zero-cost local inference, and only complex generation work reaches frontier-tier models. Every AI function has a configurable model assignment in the admin panel — the client controls cost directly, function by function.

model_trainingMulti-vendor cost matrix — part of the self-improvement layer

The model assigned to each function today is not fixed. The platform continuously benchmarks cost, latency and output quality across vendors — Claude, OpenAI, DeepSeek, Qwen and others reachable through OpenRouter — for every AI function, and maintains a live cost/quality matrix of which model is currently the best fit for each job.

This matrix is one input into the platform's Self-Healing & Improvement intelligence: as pricing shifts or a better-fit model emerges, the system flags the alternative for each function and the Ops Admin can re-assign with one click among models already integrated via OpenRouter. Bringing on a model OpenRouter doesn't yet carry — a brand-new vendor, or one with a non-standard API — is a small, occasional integration task rather than a one-click swap. Either way, the model strategy keeps getting sharper after launch instead of being locked in at delivery.

The 4-tier model hierarchy

Tasks are routed by the Model Router based on their complexity profile, not tied to a single vendor. Admins can override any assignment; models shown are current best-fit picks from the live cost matrix.

alt_routeThe Model Router — how it decides

Every AI request passes through the Model Router before any model is called. The router reads the task's complexity profile (from the admin-set assignment), checks the live cost/quality matrix for the current best-fit vendor, checks budget headroom, and routes accordingly — through OpenRouter, so swapping vendors is a config change, not a code change.

-- Model Router decision logic (simplified) def route(task: AITask) → Model: config = admin_settings(task.function_key) # per-function override if config.model_override: return config.model_override # Auto-routing by task profile — best-fit model from the live cost matrix match task.profile: case "generation_complex": return cost_matrix.best_fit("tier1") # e.g. Claude Sonnet, GPT-4o, DeepSeek-V3 case "generation_simple": return cost_matrix.best_fit("tier2") # e.g. Claude Haiku, GPT-4o mini, Qwen2.5 case "classification": return LOCAL_PHI3_MINI case "embedding": return NOMIC_EMBED_LOCAL case "kb_lookup": return VECTOR_SEARCH_ONLY # 0 tokens # Budget guard if budget.remaining(task.model) < threshold: return downgrade(task.model) # step down one tier -- Cost matrix refresh (runs continuously — part of Self-Healing & Improvement) def refresh_cost_matrix(): for vendor in ["anthropic", "openai", "deepseek", "qwen", "..."]: # via OpenRouter benchmark(vendor, metrics=["cost", "latency", "quality"]) flag_improvements_for_admin_review()

Internal second brain

The JAM Safety Knowledge Base is a continuously learning internal intelligence layer. It indexes everything that happens in the system — every document approved, every incident resolved, every staff decision made — into a vector store that can be searched semantically. Unlike a generative AI call, a KB lookup costs zero tokens. The KB is the system's long-term memory, and it gets smarter every day without additional cost.

KB architecture
memoryStorage engine — pgvector

All KB content is stored as vector embeddings in PostgreSQL via the pgvector extension — the same database that powers the rest of the platform. No separate vector DB service to maintain or pay for.

-- KB embedding schema CREATE TABLE kb_chunks ( id uuid, source_type text, -- 'incident', 'document', 'event'... source_id uuid, content text, embedding vector(768), -- nomic-embed-text (local) created_at timestamptz ); CREATE INDEX ON kb_chunks USING ivfflat (embedding vector_cosine_ops);
streamEmbedding model — local, free

Embeddings are generated by nomic-embed-text, a high-quality open-source embedding model running locally on the same server. No API call, no cost, no data leaving the system.

Why nomic-embed-text?
768-dimension vectors, Apache 2.0 licence, runs on 2GB RAM. Outperforms OpenAI ada-002 on retrieval benchmarks. Runs via Ollama on the same server.
Cost of 10,000 KB queries/month
€0.00 — all local inference, no API. Scales linearly with server CPU, not spend.
datasetWhat the KB learns from (ingestion sources)
cloud_uploadBringing JAM's existing knowledge into the system

The KB is only as valuable as the history loaded into it on day one. JAM Safety already holds years of ESMPs, RAMS, incident records, rosters and correspondence — getting that into the system is a joint workstream we plan together at the start of the build, not something dropped on either side unannounced. Heaventree builds the ingestion tooling; JAM Safety provides access to the source material; we agree the exact scope together before any import runs.

How we'll do this together
1Joint scoping session, early in the build. Heaventree and JAM Safety agree exactly which sources, formats and date ranges go into the initial load — nothing is assumed.
2Heaventree builds the ingestion pipeline for the agreed formats — parsing, chunking, embedding and source-tagging, so nothing has to be manually retyped.
3Bulk import runs alongside the rest of the build — this workstream doesn't block portal or workflow development; it progresses in parallel across the 16 weeks.
4Joint QA pass before go-live. Both teams review a sample of KB results together and sign off the dataset as live — a shared checkpoint, not a one-sided handover.
5From go-live, the continuous learning pipeline takes over (see below) — the one-time import becomes an always-on process and the KB keeps growing automatically from there.
searchHow the KB surfaces in the UI
syncContinuous learning pipeline

The KB ingestion pipeline runs asynchronously via Redis queue — events in the system publish to the queue, the worker embeds and indexes. No user action required; the KB grows automatically.

# KB ingestion pipeline event: incident.resolved → queue.publish("kb_ingest", {source: "incident", id: incident_id}) → worker.embed(incident.resolution_summary) # nomic-embed (local) → pgvector.upsert(chunk) # zero API cost event: document.approved → queue.publish("kb_ingest", {source: "document", id: doc_id}) → worker.chunk_and_embed(document.extracted_text) → pgvector.upsert_many(chunks)
Regulatory intelligence — RAG engine

JAM Safety operates across multiple jurisdictions — Ireland, UK, and potentially wider EU. Safety legislation changes. The RAG (Retrieval-Augmented Generation) engine continuously indexes current legal sources and makes them available to AI agents and staff without manual maintenance. When a new ESMP is generated for a UK event, the system pulls current UK crowd safety legislation automatically.

languageRegulatory sources indexed
updateUpdate pipeline

Regulatory sources are crawled on a schedule. Changed content triggers a re-embed and version stamp. Ops Admins are notified when a legal source updates so they can review the impact on active ESMPs.

# RAG update scheduler @cron("0 3 * * 1") # Every Monday 3am async def refresh_regulatory_index(): for source in get_active_sources(): html = await fetch(source.url) if content_hash(html) != source.last_hash: chunks = chunk_legal_text(html) embed_and_upsert(chunks, source) notify_admin(f"Regulatory update: {source.name}")
integration_instructionsHow RAG integrates with AI agents

When the ESMP Generator agent runs, it first performs a RAG lookup for the jurisdiction and event type — pulling the 5 most relevant regulatory chunks. These are prepended to the Claude prompt as grounding context. The model then generates a legally-grounded plan without hallucinating outdated rules.

# ESMP generation with RAG grounding async def generate_esmp(brief: ESMPBrief): # Step 1: RAG retrieval (local, zero tokens) legal_context = pgvector_search( query=embed(f"crowd safety {brief.jurisdiction} {brief.event_type}"), k=5, source_filter="regulatory" ) # Step 2: KB retrieval — past similar ESMPs past_esmps = pgvector_search( query=embed(f"ESMP {brief.venue_type} {brief.capacity}"), k=3, source_filter="document" ) # Step 3: Claude call (only this step costs tokens) prompt = build_prompt(brief, legal_context, past_esmps) return await claude.generate(prompt)

Self-learning & pattern detection

From day one, the platform watches for patterns — not by looking for predefined rules, but by building a baseline of normal behaviour from real data, then flagging deviations. Every new event makes the model more accurate. This is applied to staff, venues, costs and compliance simultaneously. The system surfaces patterns as intelligence, never as accusations — everything is evidence-linked.

Four pattern detection domains
model_trainingHow the self-learning engine works

The engine uses three techniques in sequence. No LLM is involved — this is statistics and local ML on structured data, which means it runs at zero token cost and improves purely from usage.

1 · Baseline profiling
For each entity (staff member, venue, subcontractor) the engine builds a rolling baseline from the last 12 months. Baseline = normal. Anything outside 2 standard deviations is a candidate flag.
2 · Vector similarity
The KB's pgvector store is used to find historically similar situations. "This incident matches 3 incidents at the same venue in 2023–2024 — all three led to a barrier failure." Evidence-backed, not guessed.
3 · Trend projection
Where a metric has been trending for 3+ consecutive events, the engine projects forward and flags expected future deviation. Gives JAM time to intervene before the problem arrives.
loopThe feedback loop — how it improves

The engine does not only observe — it learns from actions taken. When an Ops Admin dismisses a flag ("not relevant") or acts on it ("resolved: contractor replaced"), that outcome is written back to the model. Over time, false-positive rates drop and the signal-to-noise ratio improves automatically.

# Self-improvement feedback cycle event: ops_admin dismisses(flag_id, reason="false_positive") → pattern_model.record_outcome(flag, "false_positive") → pattern_model.adjust_threshold(entity_type, metric, delta=+0.15) → # Next time: flag won't fire until 2.15σ deviation (was 2.0σ) event: ops_admin acts_on(flag_id, action="subcontractor_replaced") → pattern_model.record_outcome(flag, "confirmed_true_positive") → pattern_model.increase_weight(feature_set) → # Same pattern will trigger at 1.85σ next time (more sensitive)
